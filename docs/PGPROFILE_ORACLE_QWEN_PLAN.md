# План работ: оракулы, таблица влияния, headless Qwen

## 1) Цели и зафиксированные решения

- Режим сравнения: поддержать и пары `before/after`, и серии прогонов (с разной уверенностью).
- Подход к оракулам: гибридный (сначала rule-based, затем статистический слой).
- Интерпретация влияния: показывать и "вероятное влияние", и "доказанное влияние" с явной меткой доказательности.
- Контракт таблицы влияния (v1): `parameter`, `old`, `new`, `delta%`, `affected_metric`, `direction`, `confidence`, `evidence_count`, `notes`, `workload_match_score`.
- При множественных изменениях параметров: таблицу строим, уверенность снижаем, добавляем явную пометку о низкой причинной достоверности; обязательно фиксируем "что стало лучше/хуже" и список измененных параметров.
- Интеграция Qwen: единый адаптер для двух вариантов размещения (локально и через внутренний gateway).
- UX для ИИ: максимум автосбора параметров + пресеты, ручной ввод только override.
- Ограничения на отправку данных в модель: сейчас без hard-block, но реализуем шаблон policy, который можно включить без рефакторинга.
- Критерий готовности: этапы A (таблица+экспорт+UI), B (one-click headless Qwen), C (автовалидация качества выводов).

## Этап A. Таблица влияния + экспорт + UI

### Шаг A.1 — Движок сравнения "до/после"
- Реализовать агрегацию изменений параметров между прогонами.
- Вычислять изменения ключевых метрик по секциям (WAL/DML/SQL/system metrics).
- Формировать "функциональный итог":
  - что улучшилось,
  - что ухудшилось,
  - что осталось нейтральным.

### Шаг A.2 — Построение таблицы влияния (v1)
- Генерировать строки по контракту:
  - `parameter`, `old`, `new`, `delta%`,
  - `affected_metric`, `direction`,
  - `confidence`, `evidence_count`,
  - `notes`, `workload_match_score`.
- Если изменений параметров много:
  - не блокировать вывод,
  - снижать confidence,
  - добавлять note-пояснение о множественных одновременных изменениях.

### Шаг A.3 — Поддержка серий прогонов
- Добавить режим, где сравнение строится по множеству прогонов `before` и `after`.
- Считать агрегированные эффекты (медианы/квантили/дисперсию) для устойчивости сигнала.
- Повышать confidence при консистентном эффекте на серии.

### Шаг A.4 — UI и артефакты
- Добавить в UI:
  - отдельный блок "Что стало лучше/хуже",
  - таблицу влияния с фильтрами по `impact`, `confidence`, `evidence_type`.
- Добавить экспорт:
  - `influence_table.json`,
  - `influence_table.csv`,
  - краткий markdown/wikitext-резюме для Confluence.

### Шаг A.5 — Acceptance для этапа A
- Пайплайн строит таблицу по паре и по серии прогонов.
- В таблице всегда есть `workload_match_score`.
- При множественных изменениях confidence автоматически понижается и это явно отражено в `notes`.
- UI отображает улучшения/ухудшения и позволяет фильтровать вывод.

## Этап B. Headless Qwen one-click из приложения

### Шаг B.1 — Провайдерный интерфейс LLM
- Ввести абстракцию `LLMProvider` с унифицированным `generate(...)`.
- Реализовать адаптеры:
  - `QwenLocalProvider` (локальный headless),
  - `QwenGatewayProvider` (внутренний API банка).
- Поддержать единый формат промпт-бандла и ответа.

### Шаг B.2 — Автосбор параметров и prompt bundle
- Формировать payload автоматически из артефактов анализа.
- Добавить пресеты задач (например: "краткий вывод", "рекомендации по тюнингу", "детальный RCA").
- Сохранить ручной override ограниченным набором полей.

### Шаг B.3 — Policy-template без hard-restrictions
- Добавить конфиг-policy (выключен по умолчанию), где можно определить:
  - маскирование полей,
  - allow/deny списки сущностей,
  - включение/выключение sanitization.
- В UI явно показывать, какая policy применена (даже если `none`).

### Шаг B.4 — Надежность и UX
- One-click запуск из UI с прогрессом и статусами.
- Таймауты, retry, нормализованные ошибки провайдера.
- Сохранение запроса/ответа в артефакты с trace-id для аудита.

### Шаг B.5 — Acceptance для этапа B
- Один и тот же сценарий отрабатывает через local и gateway провайдеры.
- Пользователь не вводит вручную основной набор параметров.
- Ошибки LLM-провайдера прозрачны и диагностируемы.

## Этап C. Автовалидация качества выводов (оракулы)

### Шаг C.1 — Rule-based oracle (первая линия)
- Добавить deterministic checks:
  - корректность направления эффекта (expected direction),
  - sanity по величинам изменений,
  - полнота/консистентность обязательных полей.
- Ввести oracle verdict:
  - `pass`, `warning`, `fail` + причины.

### Шаг C.2 — Статистический oracle (вторая линия)
- Для серий прогонов валидировать устойчивость эффекта:
  - consistency across runs,
  - чувствительность к шуму.
- Поднимать/понижать confidence на основании статистической стабильности.

### Шаг C.3 — Оценка LLM-вывода
- Автопроверка ответов Qwen:
  - валидность JSON/структуры,
  - отсутствие неподтвержденных claims,
  - соответствие данным таблицы влияния.
- Проставлять quality score и блокировать "финальный" статус при `fail`.

### Шаг C.4 — Acceptance для этапа C
- На тестовом наборе кейсов oracle стабильно различает "достоверные" и "сомнительные" выводы.
- Любая LLM-рекомендация ссылается на данные/метрики из артефактов.
- Есть автоматический отчет качества по каждому прогону анализа.

---

## 4) Риски и как их снижать

- Риск ложной причинности при множественных изменениях:
  - снижать confidence автоматически, помечать `probable`, повышать доказательность только на изолированных или серийных данных.
- Риск несопоставимых нагрузок:
  - обязательный `workload_match_score` и предупреждения при низком score.
- Риск vendor lock-in по Qwen-интеграции:
  - единый `LLMProvider` интерфейс + адаптеры.
- Риск будущих комплаенс-ограничений:
  - заранее встроенный policy-template (даже если сейчас отключен).

---

## 5) Definition of Done (вся инициатива)

- Есть рабочая таблица влияния по паре и серии прогонов с маркировкой доказательности и confidence.
- В UI видны улучшения/ухудшения, сопоставимость нагрузок и объяснения ограничений.
- Headless Qwen запускается one-click из приложения через единый адаптер (local/gateway).
- Выводы проходят oracle-проверки, а качество автоматически фиксируется в артефактах.
